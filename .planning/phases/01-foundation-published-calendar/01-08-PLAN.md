<objective>
Give every published event its own page that residents can open from a card, save to their calendar and share. The tracer goes first: a card on `/` links to `/events/{slug}`, the page lists the event's dates, and one date downloads as an `.ics` with a stable UID. The result is deployed and checked on real phones.

Purpose: completes ROADMAP Phase 1 success criterion 4 and the "open event pages, add them to their calendar and share them" half of the phase goal. Shared links are the main way local events spread (FEATURES: share buttons are table stakes, OG tags drive WhatsApp/Facebook previews).
Output: two migrations, EventSlug model, EventSlugger, export classes (UID, ICS, Google link), JSON-LD builder, page and share view models, event controllers and views, the first-party share module, a live check script, six test files, and a production deploy.
</objective>

## Flagged Assumptions

- **EVT-03 (unclassified edge row, flagged for manual review):** no probe category applied. Assumed coverage:
  - JSON-LD is emitted only on event pages, one object per listed upcoming occurrence, capped at `calendar.event_page_dates` (10), the same set as the visible dates list.
  - Cancelled objects keep every property and switch eventStatus to EventCancelled. Hidden and expired occurrences emit nothing.
  - EventRescheduled / previousStartDate are not emitted: Phase 1 has no "rescheduled" state, and a time edit simply moves the occurrence.
  - Paid events carry no Offer because price_text is never parsed.
  - The Google Rich Results check is manual (phone/laptop UAT), not CI.
- **URL scheme `/events/{slug}` (orchestrator outline) instead of RESEARCH Pattern 6's `/events/{id}/{slug}`.** Pure slugs read better in WhatsApp/Facebook shares. The cost is a UNIQUE slug and an `event_slugs` history table, which Task 2 adds. RESEARCH's "no slug_history table" shortcut therefore does not apply. Slugs follow the title automatically, and there is no admin slug field (discretion, keeps the single write path).
- **UID differs for one-off vs series.** RESEARCH gives `{event_id}-{recurrence_key}@…` for every occurrence. For a one-off event that would change when the admin moves its date (01-01 regenerates the key from start_date), so one-off events use `{event_id}@…` and a moved one-off updates the existing calendar entry on re-import. Turning a one-off into a series (or back) changes the shape. Those are different events in calendar terms, so this is accepted. Weekday changes to a series create new occurrence keys and therefore new UIDs (same reason).
- **The .ics DTEND for an event with no end time** is `expires_at` (start + 3h, the site's own expiry rule), and DESCRIPTION / Google details say "Finish time not given." so the guess is not shown as fact.
- **SEQUENCE** is derived from last-modified seconds since 2026-01-01 UTC. It is monotonic and fits a 32-bit integer for decades. The daily upsert touches updated_at, so SEQUENCE may rise without visible change, which is harmless.
- **Discovered-event excerpt branch of EVT-01** ("excerpt up to 200 characters plus Read more at {source}") applies to `origin = discovered`, which cannot exist until Phase 3 (Phase 3 success criterion 5 owns it). Phase 1 renders the full description for manual events. Submissions (Phase 2) also get the full description per EVT-01.
- **Attribution wording (CONTEXT discretion):** "Organised by …", "Contact: …", "Source: {note}", "More information: {host}", and "Listed by What's On Attleborough." when there is no source. **Share copy:** "{title} – {date} at {venue}, on What's On Attleborough" (D-01). **Dates shown:** the next 10 (RESEARCH Open Question 3).
- **Fallback links stay visible even when Web Share exists.** FEATURES/MDN: Web Share is not Baseline, so fallbacks are always rendered. Hiding them would add JS state for no gain.
- **Expired-page policy (EVT-05) is Phase 5.** Here a published event with no upcoming dates returns 200 with "No upcoming dates." and is not noindexed. That keeps shared links alive, matching what Phase 5 will formalise.
- **depends_on lists 01-06 and 01-07 (authoritative outline).** The plan also uses 01-04 (`UpdatePublishedEvent`) and 01-05 (`publiclyListed()`). Both finish in earlier waves, and Task 1's precondition asserts them.
- **Task size.** Each task touches more than five paths, because a tracer must cross every layer and the event page is one cohesive surface. Per-task code files stay at roughly 10-12, plus tests. The orchestrator asked for a single plan, so this is flagged instead of split.
- **No new packages.** spatie/schema-org and sabre/vobject were installed and audited in 01-01, and share.js has no dependencies, so no legitimacy checkpoint is needed.
