<objective>
Keep the iCalendar UID public contract true (WR-06) and make the edit page — the home of the status actions — survive any stored recurrence rule (WR-09).

WR-06 decision (agent's discretion, owner asked to "decide: document+accept vs fix"): FIX by blocking the one-off ↔ repeating switch in the domain action and the form, keeping the current UID scheme. This changes no public contract (UIDs stay exactly as residents and Phase 5 feeds will see them), keeps the useful property that a moved one-off date updates the same calendar entry, and is cheap now because Phase 1 is local-only and no UID has been published yet. Rejected alternatives: always `{event_id}-{recurrence_key}` (changes the published UID format for every one-off event, and a moved one-off date would then get a new UID); storing a UID per occurrence row (schema migration and backfill for no extra benefit over the guard). The admin workaround for a type change is hide + create a new event, which is plain in the form helper text, including its side effects (the hidden event's page goes offline as a 404, and the new event gets a suffixed slug such as quiz-night-2 because the hidden event keeps its slug).

Purpose: ADM-03 (edit, hide, cancel through the single choke point) and EVT-06 ("`.ics` with stable UID") must hold for every event the admin can create or a later importer can store.

MVP note: the Phase 1 ROADMAP Goal is not in user-story form (flagged in 01-VERIFICATION.md); this gap plan does not invent one.

Output: switch guard in UpdatePublishedEvent and EventForm, UID stability tests, tolerant recurrence hydration, read-only edit fallback with warning, status record actions in the events table.
</objective>
